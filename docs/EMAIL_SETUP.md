# Formspree 연동과 실제 발송 확인

현재 **BLOCKED**: 계정/수신 설정과 공개 폼 ID가 제공되지 않았고, 실제 발송·수신 확인을 수행하지 않았습니다. 로컬 코드는 구현했으며 모의 응답으로만 테스트합니다. 서비스 계정 생성이나 실제 메일 발송을 대신 수행하지 않았습니다.

## 1. 서비스 선택과 공개 범위

Formspree를 선택한 이유는 정적 페이지에서 공개 폼 엔드포인트로 POST할 수 있어 npm·UI SDK·자체 백엔드가 필요하지 않기 때문입니다. EmailJS도 과제 허용 서비스이지만 두 서비스를 동시에 사용하지 않습니다. `formId`는 제출 대상을 식별하는 공개 값이며 로그인 비밀번호나 비밀 API 키가 아닙니다. 수신 이메일은 서비스 대시보드에만 설정합니다. [공식 HTML 폼 안내](https://formspree.io/html/), [계정·폼 생성 안내](https://help.formspree.io/articles/building-your-form/building-an-html-form).

`Accept: application/json`을 사용하는 교차 출처 AJAX 제출은 공식 안내에 포함됩니다. 여기서는 라이브러리 대신 직접 `fetch`로 상태와 오류를 처리합니다. [공식 기능 안내](https://formspree.io/plans), [공식 fetch 사례](https://formspree.io/blog/formspree-ajax/).

## 2. 사용자가 직접 할 일

1. Formspree 공식 사이트에서 계정을 만들고 이메일 확인을 완료합니다. 로그인 정보나 인증 메일을 프로젝트에 복사하지 않습니다.
2. 대시보드에서 새 폼을 만들고 수신 대상 이메일을 서비스 내에서 지정·확인합니다. 자동 회신은 현재 사이트 기능에 필요하지 않습니다.
3. Integration에 표시되는 `/f/폼ID` 형식 엔드포인트를 확인합니다. 공유할 것은 **공개 폼 ID**뿐입니다. SMTP 암호, 계정 토큰, 비밀 API 키는 공유하지 않습니다.
4. 서비스의 스팸 보호·허용 도메인·현재 플랜의 제출 한도·데이터 보관 설정을 검토합니다. 한도는 변할 수 있으므로 이 문서에 고정된 월별 수치를 적지 않습니다. 도메인 제한을 켰다면 실제 Pages 도메인과 승인된 테스트 출처를 설정합니다.
5. 공개 폼 ID를 `js/config.js`의 `email.formId`에 넣습니다. **실제 전송 활성화 승인 후에만** `email.enabled`를 `true`로 바꿉니다. 이 값은 수신 주소가 아닙니다.
6. JS가 없는 화면에서도 혼동 없도록 `index.html`의 Contact 초기 안내를 활성화 상태에 맞춰 동기화합니다. JS 비활성화 시 폼은 계속 비활성입니다.
7. 아래 절차로 테스트 한 건의 실제 발송을 명시적으로 승인하고 수신함에서 확인합니다. 실제 시험을 승인하기 전에는 mock 결과만 유지합니다.

## 3. 실제 테스트 한 건

실제 발송은 사용자가 직접 하거나, 대상·내용·한 건의 발송 범위를 승인한 뒤 진행합니다.

- 로컬/배포 사이트를 열고 개인정보 고지와 `메시지 보내기` 버튼을 확인합니다.
- 본인이 승인한 테스트 이름·회신용 이메일과 식별 가능한 짧은 메시지를 입력합니다. 민감한 정보를 넣지 않습니다.
- 한 번 제출하고 Network에서 Formspree POST 응답과 화면의 접수 메시지를 확인합니다.
- Formspree 제출 목록 및 수신함/스팸함에서 같은 식별 문구가 도착했는지 확인합니다. **HTTP 접수 성공은 수신함 도착과 다릅니다.**
- CAPTCHA나 추가 확인을 요구하면 해당 공식 서비스 설정을 점검합니다. 현재 순수 fetch 구현은 별도 CAPTCHA 챌린지 UI를 자동 진행하지 않습니다. 보호를 무조건 끄지 말고 공식 통합 방법과 사용자 승인을 확인합니다.
- 접수/수신 결과를 TEST_REPORT에 날짜·출처·상태만 기록합니다. 이메일 주소와 메시지 전문이 포함된 캡처나 로그를 커밋하지 않습니다.
- 수신까지 확인한 경우에만 `release.emailLiveVerified`를 true로 갱신합니다. 설정 ID만 입력했거나 mock만 성공한 상태는 여전히 BLOCKED입니다.

## 4. 상태와 실패 처리

`submitContact()`는 `idle → invalid` 또는 `submitting → success/error`로 진행합니다. 설정 누락은 `error`와 미전송 안내로 종료하며 입력은 보존합니다. 성공 응답 후에만 `form.reset()`을 호출합니다. 전송 중에는 fieldset/버튼을 비활성화하고 같은 submit 이벤트의 재진입을 차단합니다.

| 상황 | 동작 / 사용자 조치 |
| --- | --- |
| formId 없음·형식 오류·enabled=false | 입력 검증만 하고 외부 요청 없음 |
| 422·500 등 서비스 오류 | 오류 메시지, 입력 유지, 설정 확인 후 수동 재시도 |
| 429 | 한도 안내, 자동 재시도 없음 |
| 네트워크 오류·15초 타임아웃 | 접수 여부 불명확할 수 있음. 중복 발송 전에 대시보드/수신함 확인 |
| JSON 오류·서비스 오류 객체 | 접수 성공으로 표시하지 않음 |
| 중복 클릭 | 첫 요청 완료 전 추가 요청 차단 |
| `_gotcha` 입력 | 로컬에서 요청 중단, 정상 사용자는 이 필드를 보지 않음 |

## 5. 개인정보·스팸 방어와 한계

활성 폼은 이름·이메일·메시지를 Formspree와 수신자에게 전달합니다. 이 사실을 제출 버튼 근처에서 안내합니다. 사이트 코드는 폼 값을 localStorage에 저장하지 않습니다. Formspree 측 보관·처리 정책은 운영자가 확인해야 합니다.

클라이언트 검증과 길이 제한(100/254/5000자), 중복 제출 잠금, 숨긴 `_gotcha` 필드를 구현했습니다. 서비스도 honeypot 및 스팸 보호 기능을 제공하지만 브라우저 검증은 우회할 수 있습니다. 서버 측 보호·한도·도메인 설정을 함께 사용해야 합니다. [공식 honeypot 설명](https://help.formspree.io/articles/building-your-form/honeypot-spam-filtering).

`tests/browser_checks.py`는 Formspree 호스트 네트워크를 차단하고 window.fetch를 모의 응답으로 교체합니다. `qatest00`은 테스트 안에서만 사용하는 식별자이며 실제 서비스 ID가 아닙니다. 모의 시험은 발송 완료 증거로 사용할 수 없습니다.
